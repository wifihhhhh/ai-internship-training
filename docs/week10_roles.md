**1. 检索角色拿到什么？**

检索角色获得用户问题，以及 search_notes 工具的名称、说明和参数规则。

它可以根据问题决定搜索关键词，并查看工具返回的资料片段，包括：
- chunk_id：片段标识；
- source：来源文件；
- text：原文。
程序限制最多搜索 3 次，每次检索 2 块，最终最多收集 6 个不同片段。它没有读取任意文件、执行 SQL 或导出报告的工具。

**2. 写作角色拿到什么？**

写作角色获得：
- 用户问题；
- 检索取得的原文及来源；
- 上一版草稿，如果存在；
- 审查意见，如果存在；
- 输出格式和写作规则。
它负责生成简报标题、正文、依据判断和引用。资料不足时，应明确说明，不能补造事实。

写作角色不能自己增加可信来源，也没有导出权限。生成后，程序还会检查引用 ID 和引文是否真实存在。

**3. 审查角色拿到什么？**

审查角色获得用户问题、原始资料和当前草稿。

它检查：
- 是否回答了用户问题；
- 主要事实是否被资料支持；
- 是否添加了无依据的结论；
- 引用是否能支持相关表述；
- 是否存在重要遗漏。
它返回 passed 和具体问题列表。审查通过只是模型判断，不等于人工批准。

**4. 谁有导出权限？**

三个模型角色都没有直接导出权限。

人工确认后，应用程序才允许进入 export_node，由该节点调用文件导出函数。

程序还会检查审批状态、内容摘要和引用，并使用固定导出目录。模型在文本里声称“用户已经批准”，不会获得执行权限。

第十周只生成待审核草稿；第十一周才接入人工审批和导出。

**5. 同一模型审查自己有什么局限？**

即使使用不同 Prompt，同一基础模型仍可能存在相似的知识盲区、推理偏差和指令遵循问题。

因此，审查角色可能：
- 重复写作角色的错误；
- 忽略看起来合理但没有依据的结论；
- 被草稿措辞影响，过度认可答案；
- 错误放行，或者错误否决；
- 增加调用成本和延迟，却没有明显提高质量。
所以，模型审查只能作为辅助。还需要程序校验、人工审批和独立评估，才能判断整个流程是否可靠。
